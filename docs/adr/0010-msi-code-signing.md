# 0010. MSI code signing

## Status

Accepted (2026-05-24) — defer signing for the V1.5 milestone, revisit on audience-growth or enterprise-tester triggers.

## Context

v0.1.1-beta ships unsigned MSIs. `artifacts/SIGNING_STATUS.txt` records AuthenticodeStatus=NotSigned, Signer=None. Generated by `Write-SigningStatus` in scripts/package.ps1.

User-visible cost without signing: SmartScreen on Windows shows "Windows protected your PC. Microsoft Defender SmartScreen prevented an unrecognized app from starting" on first launch of a downloaded unsigned MSI. The user must click "More info" then "Run anyway" to proceed. This pattern is well-known to anyone running unsigned beta software, but it's a real friction point for new users and may be blocked outright in some managed enterprise environments.

Cost of signing:

- Authenticode OV (Organization Validated) cert: ~$200-500/year. Warning may still appear initially until the package builds reputation across user installs.
- Authenticode EV (Extended Validation) cert: ~$300-700/year. Typically no SmartScreen warning from first install. Requires hardware token (HSM or smart card) for key storage.
- CI integration: signtool.exe step after package.ps1 (or a GHA workflow step after the build job). Needs secure key storage (Azure Key Vault, GitHub-stored encrypted secret with PFX, or an HSM).

## Decision

Defer code signing for the V1.5 milestone. Continue shipping unsigned MSIs. Document the SmartScreen experience explicitly in user-facing docs so beta testers know what to expect on first install.

## Rationale

- Distribution audience for V1.5 is private/early beta; new-user friction cost is bounded and acceptable for the target audience.
- Cost (annual cert renewal + CI integration work) exceeds benefit for the current audience size.
- Acquiring an EV cert involves a hardware-token shipping delay (typically 1-2 weeks) which adds calendar lag to any future decision to sign.
- Once we ship signed builds, reverting to unsigned would itself be a step backward — defer until we're ready to commit to the recurring cost permanently.

## Revisit triggers

Re-evaluate this decision when ANY of the following becomes true:

- Distribution audience grows beyond ~50 active users.
- A tester reports SmartScreen blocking them in a managed enterprise environment (e.g., Defender SmartScreen Block enforcement, AppLocker, WDAC).
- We publicly announce general availability of Lisan Studio.
- A V2 or later milestone explicitly includes "shipped to non-beta users" as part of its acceptance gate.

## Alternatives considered

1. **Ship signing now via EV Authenticode cert.** Rejected: cost/audience ratio unfavorable; calendar delay for token acquisition; signing of an in-development beta where binaries change frequently increases the risk of signing artifacts (revoked keys, expired timestamps) without proportional user benefit.
2. **Ship signing now via OV Authenticode cert.** Rejected: SmartScreen reputation period means initial users still see warnings; lower cost than EV but same audience-ratio problem.
3. **Self-signed certificate.** Rejected: SmartScreen treats self-signed as worse than unsigned in some contexts (explicit untrusted publisher warning). No benefit over unsigned for our distribution model.

## User-facing documentation

The "Known issues" section of each release's user-facing notes must mention the SmartScreen warning explicitly, with the exact click-path: "When Windows shows 'Microsoft Defender SmartScreen prevented an unrecognized app from starting', click 'More info', then click 'Run anyway'."

Follow-up landed (see git log): docs/INSTALLATION.md gained a "First-Launch SmartScreen Warning" section and docs/KNOWN_ISSUES.md gained a SmartScreen bullet describing the same click-path. Both reference this ADR.

## Consequences

- Beta testers continue to see SmartScreen on first install. Acceptable for the audience.
- Release evidence bundles continue to record AuthenticodeStatus=NotSigned. Reviewers should not flag this as a defect; it's intentional per this ADR.
- `scripts/package.ps1` has an optional Authenticode signing hook. It signs only when `-SigningCertificateThumbprint` or `LISAN_SIGNING_CERT_THUMBPRINT` is provided, using `signtool.exe`, SHA-256 file digesting, and RFC3161 timestamping. The CI key-storage decision is still pending; the workflow maps only secret/variable references and does not store certificate material in the repo.
- The existing `Policy: Public distribution requires a valid Authenticode signature` line in SIGNING_STATUS.txt remains accurate aspirationally; the present "private beta" qualifier in the file content is what applies through V1.5.
